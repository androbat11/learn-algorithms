The Problem Contract

Five lines to write before any code. Print this. Keep it next to the keyboard until it is automatic.

Algorithms & Data Structures workspace · Companion to Lesson 1

The five lines

1 · Given

Every input, with its type and shape. Not "an array" — "an array of number, possibly empty, possibly with duplicates."

Ask: What exactly am I handed? What type is each thing? Can it be empty, null, or negative? Is it sorted? Are duplicates allowed?

2 · Goal

The exact thing to return, as a type. The single most common ambiguity in all of interviewing is values versus indices.

Ask: What type comes back? What if several answers are valid — any one, or all of them? What is returned when no answer exists?

3 · Bounds

The numeric limits. These are not trivia: bounds tell you which complexity is acceptable, which means they tell you the approach.

Ask: How large can the input get? What range do the values span? Is there a time or memory limit implied?

4 · Trace

Three parts, and it is not finished until all three are there:

  1. A concrete input — real values, not "an array of numbers"
  2. The steps — the work, written out
  3. The output — the actual answer

An input with no output is not a trace. It is the most common way this line gets faked, because writing the input feels like progress and the output is where the thinking actually happens.

Ask: Can I produce the answer myself, slowly, without code? Does it match the one I was given?

5 · Breaks

The inputs that would embarrass you. Write them down now, while it is cheap, rather than discovering them in front of an interviewer.

Ask: What is the smallest legal input? What if everything is identical? What if nothing matches?

Choosing a trace that is worth writing

Any input will produce an answer. A good input produces an answer that would catch you being wrong. Three rules:

Rule 1 · Small enough to finish by hand

Three to five elements. If you cannot complete it on paper in under a minute, it is too big and you will skip the step — which defeats the point.

Rule 2 · Not a degenerate case

Empty, single-element, and all-identical inputs belong on the Breaks line. The Trace should be an ordinary, interesting case — the one that shows the algorithm actually working.

Rule 3 · The answer must not be the first thing you check

This is the one people miss. If the answer sits at the very front, a broken implementation that always returns the first thing will pass your trace, and you will believe you understand the problem when you do not.

Worked example — the difference one number makes

nums = [3, 4, 5, 6], target = 7  →  answer [0, 1]. Found on the first of six pairs. A function that ignores its input and returns [0, 1] passes this trace.

nums = [3, 4, 5, 6], target = 11  →  answer [2, 3]. Now all six pairs are checked and the answer is the last one. Same array, one number changed, and the trace went from proving nothing to exercising the whole loop.

Two flavours of trace

Problem trace — for "solve this": input, the reasoning, output.

// Trace: nums = [3, 4, 5, 6], target = 11
//        3+4=7  3+5=8  3+6=9  4+5=9  4+6=10  5+6=11 ✓
//        -> [2, 3]   (indices, not values)

Algorithm trace — for "implement this": the state after each step. Use a table; it is how you find an off-by-one before you write it.

// Trace: insertion sort on [5, 2, 4, 1]
//   start   [5]        2 4 1
//   i=1     [2 5]      4 1      2 slid past 5
//   i=2     [2 4 5]    1        4 stopped at 2
//   i=3     [1 2 4 5]           1 went to the front
The trace has a second job

It becomes your first test case, for free. You have already written the input and the expected output in the format a test needs. Every trace you finish is a test you do not have to invent later — and the Breaks line supplies the rest of the suite.

Bounds → what they are telling you

Interviewers state input sizes for a reason. Read the size as a hint about the complexity you are expected to reach.

If n is about…You probably need…
n ≤ 10Anything. Even generating every permutation, O(n!)
n ≤ 20Exponential is survivable — O(2ⁿ) subsets, backtracking
n ≤ 500O(n³) is fine
n ≤ 5,000O(n²) is fine
n ≤ 10⁶O(n log n) — sort, heap, or binary search
n > 10⁶O(n) or O(log n). One pass, hash map, two pointers
How to use this

Read it backwards. If the bound is 10⁵ and your idea is a nested loop, the bound has already told you the idea is wrong — before you wrote a line. That is thirty seconds saved that would otherwise have been ten minutes lost.

Standard clarifying questions

Ask two or three of these on every problem. They are cheap, they are always reasonable, and they buy thinking time that looks like diligence.

  • Should I return the values, or the indices?
  • Can the input be empty?
  • Are duplicates possible?
  • Can values be negative? Zero?
  • Is the input already sorted?
  • Is exactly one valid answer guaranteed?
  • If several answers are valid, is any one acceptable?
  • What should I return when there is no answer?
  • May I modify the input in place?
  • How large can the input get?
  • Can the same element be used twice?
  • Does case, whitespace, or Unicode matter?

Standard breaks

The usual suspects. Run a new problem past this list and something will almost always stick.

  • Empty input — [], "", null
  • One element
  • Two elements — the smallest interesting case
  • All elements identical
  • Already sorted, and sorted backwards
  • Negative numbers, and zero
  • No valid answer exists
  • Every answer is valid
  • Integer overflow on a sum or product
  • Target is the first, or the last, element
  • Duplicates of the thing being searched for
  • Single-character or single-node structures
