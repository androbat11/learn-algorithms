Here is the thing nobody says out loud about bubble sort: it is not a bad algorithm because it is slow. Merge sort is coming and it is faster, but that is not the point. Bubble sort is a bad teacher, because you can write it correctly without ever being able to say why it works. You just push big things rightward until nothing moves, and it sorts, and you shrug.

Insertion sort is the same complexity class and it is a far better teacher, because it comes with a sentence you can check at every step. That sentence is called a loop invariant, and it is the single most useful tool for reasoning about code you have not run yet — which is exactly the situation you are in at a whiteboard.

The ideaOne sentence, true the whole way through

Insertion sort is how you sort a hand of playing cards. The cards on the left are already in order. You pick up the next one and slide it leftward until it sits in the right place. Repeat.

The invariant is the promise that makes it work:

The loop invariant

At the start of each iteration of the outer loop, the first i elements are sorted among themselves.

Read that carefully, because there is a trap in it. Sorted among themselves is not the same as in their final positions. Element 0 might still get displaced later by something smaller arriving from the right. That distinction is the whole difference between insertion sort and selection sort, and interviewers do ask it.This is the standard CLRS treatment: an invariant is proved in three parts — initialization (true before the loop), maintenance (each pass preserves it), and termination (when the loop ends, it gives you what you wanted). CS360 — insertion sort and loop invariants; Stanford CS161, Lecture 1 (PDF).

Check the three parts yourself. Initialization: before the first pass, i = 1, and one element is trivially sorted. Maintenance: each pass slides element i into the sorted region, making it i + 1 long. Termination: the loop ends when i reaches the length, so all n elements are sorted among themselves — which, when it is all of them, does mean final positions.

In RustThe loop that panics

Every textbook writes insertion sort roughly like this, and it is correct — in C. Translate it directly into Rust and it detonates:

// ✗ Translated straight from C. Do not use.
fn insertion_sort(a: &mut [i32]) {
    for i in 1..a.len() {
        let key = a[i];
        let mut j = i - 1;

        while j >= 0 && a[j] > key {   // warning: comparison is useless
            a[j + 1] = a[j];
            j -= 1;                     // 💥 panics when j reaches 0
        }
        a[j + 1] = key;
    }
}

Two things go wrong, and both come from the same fact: j is a usize, and a usize cannot be negative.

First, j >= 0 is always true. The compiler even tells you — unused_comparisons, "comparison is useless due to type limits" — but it is a warning, not an error, so it compiles and you get to find out at runtime. Second, when j is 0 and you write j -= 1, there is no negative to go to. In a debug build that panics with attempt to subtract with overflow. In a release build it silently wraps to usize::MAX, and then a[j] panics on the index instead — index out of bounds: the len is 4 but the index is 18446744073709551615. Different message, same crash. Both of those are real output; run it yourself at the end of this lesson.

Worth keeping

This is not a trivia question — it is the shape of a whole category of Rust bug. Any downward loop over indices is a place where usize underflow is waiting. In an interview, saying "careful, j is unsigned here" before you write the loop is exactly the signal a Rust interviewer is listening for.

The version that works

The fix is not a cast. It is to reformulate the loop so the index never needs to go below zero — compare backwards from j instead of sitting at j - 1:

fn insertion_sort(a: &mut [i32]) {
    for i in 1..a.len() {
        let mut j = i;
        while j > 0 && a[j - 1] > a[j] {
            a.swap(j - 1, j);
            j -= 1;
        }
    }
}

Read what changed. j starts at i, not i - 1. The guard is j > 0, which is a real condition rather than a tautology, and it short-circuits before a[j - 1] is ever evaluated at j == 0. And a.swap(j - 1, j) does the exchange without you holding two mutable borrows at once — which is the thing the borrow checker would otherwise stop you doing.

There is a quiet bonus. Empty and single-element slices need no special case: 1..0 and 1..1 are both empty ranges in Rust, so the loop simply never runs. Two of the Breaks from Lesson 1, handled by construction rather than by an if.Honest footnote: this swap-based version does three writes per step where a shift-based one does one. The standard library uses shifting — insertion_sort_shift_left. Clarity first; you can optimise once you can write it without thinking.

Why it mattersThe algorithm that is actually in std

Insertion sort is O(n²) in the worst case, and you will hear it dismissed for that. But look again at the trace, at the 4 that stopped after two comparisons. On input that is already sorted, every inner loop exits on its first test, and the whole thing runs in O(n). Insertion sort is adaptive: it gets faster the closer the input already is to sorted. It is also stable — equal elements keep their relative order, because the guard is > and not >=.

Which is why this is not a toy. Rust's standard library sort is a hybrid, and below a small-length threshold it hands the work to insertion_sort_shift_left — roughly twenty elements or fewer, per the driftsort design writeup. Every time you call .sort() on a small Vec, this is the code that runs.
