Here is the thing nobody says out loud about bubble sort: it is not bad because it is slow. It is bad because you can write it correctly without ever being able to say why it works. You push big things rightward until nothing moves, it sorts, and you shrug.

Insertion sort is the same complexity class and a far better teacher, because it comes with a sentence that is true at every step. That sentence is called a loop invariant, and it is the most useful tool there is for reasoning about code you have not run — which is exactly your situation at a whiteboard, and exactly what was missing when you froze.

The ideaSorting a hand of cards

You already know this algorithm; you have just never written it. It is how you sort a hand of playing cards. The cards on the left are in order. You pick up the next one and slide it leftward until it sits in the right place. Repeat until there are no cards left to pick up.

The invariant is the promise that makes it work:

The loop invariant

At the start of each pass, the first i elements are sorted among themselves.

There is a trap in that sentence, and it is worth slowing down for. Sorted among themselves is not the same as in their final positions. The element at index 0 can still be displaced later by something smaller arriving from the right. That distinction is the entire difference between insertion sort and selection sort, and it is a real interview question.This is the standard CLRS treatment. An invariant is proved in three parts: initialization (true before the loop), maintenance (each pass preserves it), termination (when the loop ends it gives you what you wanted). CS360 — insertion sort and loop invariants; Stanford CS161, Lecture 1 (PDF).

Check the three parts yourself. Initialization: before the first pass, i = 1 and one element is trivially sorted. Maintenance: each pass slides element i into the sorted region, making it one longer. Termination: the loop ends when i reaches the length — so all n elements are sorted among themselves, which, when it is all of them, does mean sorted.

Look closely at pass i = 2. The 4 compared against 5, moved, compared against 2, and stopped. It did not walk the whole array. That early stop is where insertion sort's real advantage lives, and you are going to measure it yourself in Exercise 3.

The codeEight lines

function insertionSort(a: number[]): void {
  for (let i = 1; i < a.length; i++) {
    let j = i;
    while (j > 0 && a[j - 1] > a[j]) {
      [a[j - 1], a[j]] = [a[j], a[j - 1]];   // swap
      j--;
    }
  }
}

Three details worth naming, because each one is a decision:

  • i starts at 1, not 0. Element 0 is already a sorted region of one, so there is nothing to do for it.
  • The guard is j > 0, checked before a[j - 1]. JavaScript short-circuits &&, so a[-1] is never evaluated. Reverse those two conditions and you get undefined comparisons instead of a crash — which is worse, because it fails silently.
  • The comparison is >, not >=. That single character is what makes this sort stable: equal elements never swap past each other, so they keep their original relative order.

Empty and single-element arrays need no special case. a.length is 0 or 1, the loop never runs, and the array is returned untouched. Two of the Breaks from Lesson 1, handled by construction.

Exercise 1 · the primitive

Before the whole sort, build the piece it is made of. Given an already sorted array and a value, return a new array with the value inserted in the right place. Do not use .sort().

Hint

Copy with sorted.slice(). Push value onto the end — it is now at index out.length - 1. Then run exactly the inner loop of insertion sort on it: while it is not at index 0 and the element to its left is bigger, swap them and step left.

Solution 
function insertOne(sorted, value) {
  const out = sorted.slice();
  out.push(value);
  let i = out.length - 1;
  while (i > 0 && out[i - 1] > out[i]) {
    [out[i - 1], out[i]] = [out[i], out[i - 1]];
    i--;
  }
  return out;
}

That while loop is insertion sort's inner loop. You have already written the hard half.

Exercise 3 · measure the claim

Do not take my word that insertion sort is fast on nearly-sorted input — measure it. Return the number of swaps performed while sorting. Leave the caller's array untouched.

Hint

Take your Exercise 2 answer. Change the first line to const b = a.slice(), sort b instead of a, add let count = 0 at the top, increment it inside the while loop, and return count.

Solution 
function countShifts(a) {
  const b = a.slice();
  let count = 0;
  for (let i = 1; i < b.length; i++) {
    let j = i;
    while (j > 0 && b[j - 1] > b[j]) {
      [b[j - 1], b[j]] = [b[j], b[j - 1]];
      j--;
      count++;
    }
  }
  return count;
}
Look at what you just proved

Two of those cases are the whole point. A sorted array of six elements costs zero swaps. A reversed array of four costs six — which is 4 × 3 ÷ 2, the number of pairs. That gap is the difference between O(n) and O(n²), and you did not have to trust anybody about it. You ran it.

Why it mattersAdaptive and stable

Insertion sort is O(n²) in the worst case and you will hear it dismissed for that. But your Exercise 3 results are the counter-argument. On input that is already sorted, every inner loop fails its first test and the whole thing is O(n). Insertion sort is adaptive: the closer the input is to sorted, the faster it goes. Merge sort, which is next lesson, is not — it does the same work regardless.

It is also stable, thanks to that > instead of >=. Stability matters the moment you sort records rather than numbers: sort by name, then by department, and a stable sort leaves each department's names still in order.

These two properties are why insertion sort is not a museum piece. Real sorting implementations are hybrids that switch to it for small or nearly-sorted runs — including Rust's standard library, which hands off to an insertion sort below a small-length threshold.Rust std source: insertion_sort_shift_left, used below SMALL_SORT_FALLBACK_THRESHOLD.
