Merge Sort

The first algorithm that beats O(n²), and the first where recursion does the work. The trick is that the recursion is the easy half — almost nobody tells you that.

≈25 minutes · TypeScript · Follows Lesson 3 · Card: Sorting

First · from memory

Two things from Lesson 2, no scrolling. What is insertion sort's loop invariant, and how many swaps does it do on an already sorted array of six elements?

Invariant · zero swaps

Invariant: at the start of each pass, the first i elements are sorted among themselves — not in their final positions.

Swaps on sorted input: zero. You measured it in Exercise 3. Every inner loop failed its first test. Hold on to that number; this lesson is going to put it next to merge sort's, and they do not behave the same way at all.

Insertion sort has a ceiling and you can compute exactly where it is. At n = 1,000 it does roughly 10⁶ operations and nobody notices. At n = 100,000 it does 10¹⁰, and you have written something that will not finish while you watch. That gap is the entire reason a second sorting algorithm exists.

Merge sort gets to O(n log n), and at n = 100,000 that is about 1.7 million operations instead of ten billion — roughly six thousand times less work. Here is how it gets there.

The ideaMerging is the algorithm

Merge sort is usually taught as "split the array in half, sort each half, merge them," and then people spend an hour trying to hold the recursion in their head and conclude they are bad at recursion.

They are not. The framing is just backwards. Here is the honest version:

The thing to understand

Merging two already-sorted arrays into one sorted array is the algorithm. The recursion is four lines of bookkeeping on top. If you can write merge, you have written merge sort — the rest follows almost mechanically.

So we build merge first, in isolation, where there is no recursion to think about at all. It is a loop over two arrays with two pointers.Two pointers walking two sorted sequences is a pattern in its own right, and you will meet it again on its own terms later. Here it arrives as a component rather than as a topic.

How merging works

You have [1, 3, 5] and [2, 4, 6]. Put a finger on the front of each. Repeatedly take the smaller of the two things under your fingers, and advance that finger. When one array runs out, everything left in the other is already sorted and already larger — so just append it.

left  [1, 3, 5]      right [2, 4, 6]      out []
       ^                    ^
1 <= 2  → take 1            out [1]
3 <= 2? no → take 2         out [1, 2]
3 <= 4  → take 3            out [1, 2, 3]
5 <= 4? no → take 4         out [1, 2, 3, 4]
5 <= 6  → take 5            out [1, 2, 3, 4, 5]
left is empty → append the rest of right
                            out [1, 2, 3, 4, 5, 6]
Exercise 1 · the algorithm

Given two arrays that are each already sorted, return one sorted array containing everything. Do not use .sort(). Do not modify the inputs.

Hint

Three loops, one after another. First: while (i < left.length && j < right.length) — push the smaller and advance only that index. Then while (i < left.length) to drain what is left. Then the same for j. Only one of those last two ever runs.

Use <= and not < in the comparison, for the same stability reason as Lesson 2.

Solution 
function merge(left, right) {
  const out = [];
  let i = 0, j = 0;
  while (i < left.length && j < right.length) {
    if (left[i] <= right[j]) out.push(left[i++]);
    else                     out.push(right[j++]);
  }
  while (i < left.length)  out.push(left[i++]);
  while (j < right.length) out.push(right[j++]);
  return out;
}

O(n + m) time — every element is looked at once. That linearity is what makes the whole thing work.

The recursionFour lines on top

Now the easy half. To sort an array: if it has fewer than two elements it is already sorted, so hand it back. Otherwise cut it in half, sort each half the same way, and merge the two results.

The part that feels like a leap is trusting that mergeSort(left) returns a sorted array when you have not finished writing mergeSort yet. It does. Every recursive call gets a strictly smaller array, and arrays of length 0 or 1 stop immediately — so the whole thing bottoms out. That stopping condition is the base case, and forgetting it is how you get a stack overflow.

Trace it first

Before writing code — this is the algorithm trace from the contract card. Split [5, 2, 4, 1] all the way down, then merge it back up. Write every intermediate array.

The trace 
split   [5,2,4,1]
        [5,2]      [4,1]
        [5] [2]    [4] [1]
merge   [2,5]      [1,4]
        [1,2,4,5]

Four levels down, four levels back. Notice nothing is compared on the way down — the splitting is pure bookkeeping. All the actual work happens on the way back up, in merge.

Exercise 2 · the recursion

Return a new sorted array. Your merge from Exercise 1 is already provided below — you only need to write the four lines of mergeSort.

Hint

if (a.length <= 1) return a.slice(); — the copy matters, so callers never get a reference to the original.

Then const mid = Math.floor(a.length / 2), a.slice(0, mid) and a.slice(mid). Call mergeSort on each and pass both to merge.

Solution 
function mergeSort(a) {
  if (a.length <= 1) return a.slice();
  const mid = Math.floor(a.length / 2);
  const left  = mergeSort(a.slice(0, mid));
  const right = mergeSort(a.slice(mid));
  return merge(left, right);
}

Five lines, and four of them are bookkeeping. The sorting happens entirely inside merge — which you wrote first, on purpose.

Why n log nCount the levels

Two facts multiplied together. Take [8, 7, 6, 5, 4, 3, 2, 1]:

level 0 [8, 7, 6, 5, 4, 3, 2, 1] level 1 [8, 7, 6, 5] [4, 3, 2, 1] level 2 [8, 7] [6, 5] [4, 3] [2, 1] level 3 [8] [7] [6] [5] [4] [3] [2] [1] — then merge back up — level 2 [7, 8] [5, 6] [3, 4] [1, 2] level 1 [5, 6, 7, 8] [1, 2, 3, 4] level 0 [1, 2, 3, 4, 5, 6, 7, 8]
  • How many levels? You halve until you reach 1. From 8 that is 8 → 4 → 2 → 1, three halvings. That is log₂ n. Doubling the input adds one level, not double the work — this is why the algorithm scales.
  • How much work per level? Every level touches all n elements exactly once during merging, no matter how they are grouped. That is O(n).

Multiply: O(n log n). Not because of a formula you memorised, but because you counted the levels and counted the work on each.

The tradeWhat it costs you

Merge sort is not free, and knowing what you gave up is the kind of thing interviewers probe.

Space. Insertion sort sorts in place — O(1) extra. Merge sort builds new arrays at every level, so it needs O(n) extra memory. That is the price of the speed.

Adaptivity. Insertion sort noticed when its input was already sorted and did nothing. Merge sort cannot notice. It splits all the way down and merges all the way back regardless — the shape of the input never changes what it does. Do not take my word for it. Measure it.

Exercise 3 · measure the claim

Both functions are given below, working. Add counting: return how many times an element from the left half is compared against one from the right half — that is, one count per iteration of the main while loop. The two draining loops compare nothing.

Hint

One line. count++ as the first statement inside the main while (i < left.length && j < right.length) loop — before the if, because the comparison happens whichever branch is taken. Nothing else changes.

Solution 
while (i < left.length && j < right.length) {
  count++;                                    // <- the only new line
  if (left[i] <= right[j]) out.push(left[i++]);
  else                     out.push(right[j++]);
}

The counter lives in the enclosing function, so both inner functions can reach it — a closure, which is also why sort and merge are nested rather than top-level.

Now put the two side by side

InputMerge sort
comparisons		Insertion sort
swaps
[1,2,3,4] sorted40
[4,3,2,1] reversed46
[1..8] sorted120
[8..1] reversed1228

Read the middle column: 4, 4, 12, 12. Merge sort does the same work on sorted input as on reversed input — it is not adaptive. Now read the right column: 0, 6, 0, 28. Insertion sort collapses to nothing when the input is already sorted, and blows up when it is reversed.

That is the real trade, and it is why serious sorting implementations use both: something O(n log n) for the bulk, falling back to insertion sort on small or nearly-sorted runs where its adaptivity wins.
