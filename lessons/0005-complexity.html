Complexity

You have been quoting Big-O for four lessons. Now you learn to read it off the shape of the code in about three seconds — and, more usefully, to run it backwards: from the constraint line to the solution you are allowed to write.

First · the rep you owe, cold

Yesterday's rep was merge from a blank file. Here is the blank file. Two already-sorted arrays in, one sorted array out. No .sort(), no mutation of the inputs, no scrolling back to Lesson 4 — a wrong answer you then fix is worth more than a right answer you copied.

Two indices, i into left and j into right. While both still have elements, push the smaller and advance only that index. When the while ends, exactly one array has leftovers — append the rest of both, since one of the two appends does nothing.

function merge(left, right) {
  const out = [];
  let i = 0, j = 0;
  while (i < left.length && j < right.length) {
    if (left[i] <= right[j]) out.push(left[i++]);
    else                     out.push(right[j++]);
  }
  while (i < left.length)  out.push(left[i++]);
  while (j < right.length) out.push(right[j++]);
  return out;
}

<= rather than < is what makes merge sort stable: on a tie the left element goes first, so equal elements keep their original order.

There are two complexity skills and only one of them gets taught. The first is reading Big-O off code you are looking at. The second is reading it off a constraint line before you have written anything — and that one is the reason this lesson exists, because it is the fix for freezing at a blank editor. A bound tells you which family of solutions is permitted. That is a much smaller room to search than "all possible algorithms."

Part oneReading it off the code

Big-O is not something you derive. It is a shape you recognise, and there are about nine shapes. Four steps, every time:

  1. Find the innermost line that does real work

    A comparison, a swap, a hash lookup. Ignore the loop headers, the declarations, the early returns.

  2. Count how many times it runs, in terms of n

    Roughly. You want the shape, not the number.

  3. Drop constants and lower-order terms

    3n² + 90n + 7 is O(n²). Not approximately — exactly, by definition.

  4. Add the hidden loops

    This is the step people skip, and it is where most wrong answers come from. Every call inside your loop carries its own cost.

The shapes themselves, with where you have already met each one:

ComplexityThe shapeYou have seen it in
O(1)No loop over the input at all.map.get(k)

O(n · m)Two nested loops over two different inputs.—

O(n!)Every remaining element tried at every position.—

Two of those need care, and both of them you have already written.

Care one: sequential loops add, nested loops multiply

This single distinction settles most complexity arguments. Two loops one after another is O(n + n) = O(n). One loop inside another is O(n × n) = O(n²). Merge sort's merge has three while loops and is O(n), because they run in sequence and between them they touch each element once. Three loops, linear.Which is why "how many loops are there?" is the wrong question and "are they nested?" is the right one. Counting loops is how people talk themselves into O(n³) on linear code.

Care two: the triangular loop is still quadratic

Insertion sort's inner loop does not run n times. It walks back over the sorted prefix, so on pass i it does at most i comparisons. Total: 1 + 2 + … + (n−1), which is n(n−1)/2. Half of n². So is it O(n) — the average pass being n/2 — or O(n²)?

Do not take my word for it. Instrument it.

Exercise 2 · measure the claim

Write the triangular nested loop — outer i from 0 to n−1, inner j from 0 to i−1 — and return the exact number of times the inner body runs. This is insertion sort's comparison count in the worst case, with the sorting removed.

Outer loop i from 0 while i < n. Inner loop j from 0 while j < i — note i, not n. Increment ops inside the inner loop. On the first outer pass the inner loop runs zero times, which is correct and is why triCount(1) is 0.

function triCount(n) {
  let ops = 0;
  for (let i = 0; i < n; i++) {
    for (let j = 0; j < i; j++) {
      ops++;
    }
  }
  return ops;
}

Now read the numbers you just produced against n²:

n n² actual ratio 10 100 45 0.450 100 10,000 4,950 0.495 1000 1,000,000 499,500 0.4995

The ratio is converging on exactly ½, and it will never move again. That is what "O(n²) with a constant factor of a half" looks like when you measure it instead of asserting it.

Why the half does not rescue you

Halving the work is real. 499,500 comparisons genuinely beat 1,000,000, and on a nearly-sorted array insertion sort does better still — you measured that in Lesson 2. None of it changes the complexity, because Big-O answers exactly one question: what happens when n doubles?

Double n from 1,000 to 2,000 and the count goes from 499,500 to 1,999,000 — four times the work, both before and after the ½. The constant cancels out of the only question being asked. That is not the notation being sloppy; that is the notation being about something.

Care three, the one that is specific to JavaScript

Step 4 — add the hidden loops — matters more in TypeScript than in most languages, because the standard library hides linear work behind single-token method calls. All of these are loops:

Looks like one operationActuallyBecause
arr.includes(x)O(n)Linear scan of the array.
arr.indexOf(x)O(n)Same scan, returning a position.
arr.shift()O(n)Every remaining element moves down one index.
arr.slice(), [...arr]O(n)Copies, and allocates the copy.
s += x in a loopO(n²)Strings are immutable; each += copies the whole string.
map.get / set.hasO(1)*Hashing. This is why Two Sum works.
arr.push / arr.popO(1)*At the end, nothing needs to move.

* Average and amortised respectively. Say the qualifier out loud in an interview — it is the difference between having memorised a table and understanding it.

arr.includes(x) inside a loop over arr is two nested loops wearing one line of code, and it is the single most common way a candidate writes O(n²) while believing they wrote O(n).

Part twoThe log, measured

O(log n) is the one shape that is genuinely hard to feel, because the numbers are absurd and reciting them does not help. So produce them.

Exercise 3 · measure the log

Return how many times you can halve n — rounding down each time — before it reaches 1. This is the number of comparisons binary search makes, and the depth of merge sort's recursion tree.

A while loop that continues while n > 1. Inside it, n = Math.floor(n / 2) and steps++. Nothing else. If n starts at 1 the loop never runs, which is the correct answer of 0.

function halvings(n) {
  let steps = 0;
  while (n > 1) {
    n = Math.floor(n / 2);
    steps++;
  }
  return steps;
}

That loop is the definition of log₂ (floored). Whenever you see a variable being halved toward a fixed target, the loop count is log n — and you never need to compute a logarithm to know it.

Nineteen. A million elements, nineteen comparisons. Put that next to the other two shapes on the same input and the reason complexity is worth an entire lesson becomes a single line of arithmetic:

at n = 1,000,000 … O(log n) 19 instant O(n) 1,000,000 instant O(n log n) ~20,000,000 a fraction of a second O(n²) 1,000,000,000,000 about three hours

Same input. Same machine. The gap between the third row and the fourth is the gap between a solution and a failed interview, and it is visible in the code before you run it — the fourth row is the one with the nested loop.

Part threeRunning it backwards

Here is the part that fixes the blank editor, and the specific gap in the contract you sent me for Two Sum. You wrote the constraint down — 2 <= nums.length <= 1000 — and then drew no conclusion from it. A bound you have recorded but not cashed in is just a number sitting on the page.

Cashing it in needs exactly one fact, and it is the only number in this lesson worth memorising: a modern machine performs a few hundred million simple operations per second. Roughly 10⁸ as a conservative figure, per the USACO Guide; "some hundreds of millions" in Laaksonen's Competitive Programmer's Handbook. With that one number, a bound becomes a verdict.

n up toAffordableWhich usually means
10O(n!)Try every permutation. Backtracking.
20–25O(2ⁿ)Every subset. Take-it-or-leave-it recursion.
500O(n³)Three nested loops are fine.
5,000O(n²)Brute-force every pair.
10⁶O(n log n)Sort first, then one pass.
10⁷ and upO(n)Hash map, two pointers, sliding window.
10¹⁸O(log n)Binary search, or arithmetic. You cannot read the input.

These are order-of-magnitude heuristics, not laws, and the two sources disagree at the edges — Laaksonen puts the O(n²) line at n ≤ 5,000, the USACO Guide at n ≤ 7,500. Treat that disagreement as the point rather than as a problem: you are choosing between 10⁶ and 10¹⁰ operations, never between 5,000 and 7,500.

What your Two Sum bound actually said

n ≤ 1000. So O(n²) is 10⁶ operations, which runs in well under a second. The expected answer here is "brute force is too slow," and the expected answer is wrong:

The verdict line, out loud

"n is at most 1,000, so a double loop is about a million operations — comfortably under a second. Brute force is allowed here. I will still write the hash map, because O(n) is easier to get right than a careful nested loop with an index-reuse bug in it."

That is a stronger answer than the rehearsed one, for two reasons. It is true. And it demonstrates that you converted the bound rather than pattern-matching the problem to a memorised complexity — which is the difference an interviewer is actually listening for.

SpaceIn one paragraph

Space complexity is extra memory beyond the input, and it is the sum of two things: what you allocate that grows with n, and the maximum depth of your recursion — not the total number of calls, the deepest the stack ever gets. So merge sort is O(n) space: the arrays it allocates dominate its O(log n) stack. Insertion sort is O(1): a few index variables, whatever n is. A handful of counters is never O(n), however many of them you declare.

Today's rep

  1. Cash in the bound on your own contract

    Go back to the Two Sum contract you sent me and add one line to Bounds: "n ≤ 1000 → n² is 10⁶ → quadratic is allowed." One line. This is the one gap in that contract I have not seen you close, and from now on every contract you write should carry a verdict, not just a number.

  2. Predict from constraints alone

    Open any problem on Grind 75. Read only the constraints — do not read the problem. Write down the complexity you expect to need and the pattern it implies. Then read the problem and check. Two minutes, and it trains the exact instinct that replaces the freeze.
